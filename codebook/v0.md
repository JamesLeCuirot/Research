# AFACS codebook v0

*Status: draft for calibration. Author: James Le Cuirot. Sections 1–4 are James's draft, unchanged. Section 5 holds operational notes proposed by Claude Code to make the codebook testable; each is marked **[proposed]** and stays only if James accepts it. Codebook decisions are James's.*

AFACS adapts the Human Factors Analysis and Classification System (HFACS; Shappell & Wiegmann, 2000), which builds on Reason's Swiss-cheese model, to failures of LLM multi-agent systems. Each failed trace is coded at **every layer where there is evidence** (multi-label). Each trace also gets a **deepest contributing layer** and a **confidence** rating (high/medium/low).

## 1. Layers and codes

### L4 — Organisational / design influences
Decisions made by whoever built or deployed the system.
- `L4.1` Architecture and role design: bad role split, missing verifier, no termination logic.
- `L4.2` Resource provisioning: tools missing or inadequate, step or token budgets, context limits.
- `L4.3` Process: the framework has no standard procedure for verification or handover.

### L3 — Supervision / orchestration
The orchestrator or manager agent, the task specification and system prompt, and verification layers.
- `L3.1` Inadequate supervision: no check on subagent output.
- `L3.2` Planned inappropriate operation: a task assigned beyond an agent's capability or information.
- `L3.3` Failure to correct a known problem: a loop or error is visible in the trace and nobody intervenes.
- `L3.4` Deficient specification: an ambiguous, contradictory or incomplete task or prompt.

### L2 — Preconditions
- `L2.1` Environment: tool or API failures, bad or unavailable information.
- `L2.2` Agent state: context saturation, earlier instructions lost, carry-over from an earlier error.
- `L2.3` Coordination (the crew resource management analogue): communication breakdown, information withheld, another agent's input ignored. MAST category 2 (inter-agent misalignment) mostly lands here.

### L1 — Unsafe acts

**Errors**
- `L1.E1` Skill-based: an execution slip, such as a malformed tool call or a syntax error in otherwise correct intent.
- `L1.E2` Decision: a wrong plan or choice given adequate information.
- `L1.E3` Perceptual: a misread observation, tool output or prior message.

**Violations**
- `L1.V1` Routine: habitual shortcutting across the trace, such as consistently skipping verification.
- `L1.V2` Exceptional: a one-off departure, such as fabricating a result, falsely claiming completion, editing tests to pass, or hardcoding outputs.
- `L1.V?` Indeterminate: all three violation criteria hold but the evidence is thin (see section 2).

## 2. Violation evidence rule

A failure is coded as a **violation** only if all of these hold:

1. The requirement was in the agent's accessible context.
2. The trace shows the agent represented it, by referencing or acknowledging it, **or** the deviation is of a kind that cannot plausibly be accidental (for example, hardcoding expected test outputs).
3. The agent proceeded otherwise.

If all three hold but evidence is thin, use `L1.V?` (indeterminate). Otherwise code it as an error.

This is a **behavioural** classification, not a claim about model intent or mental states.

## 3. Output fields (one row per trace)

`trace_id, framework, model, mast_labels, l4_codes, l3_codes, l2_codes, l1_codes, deepest_layer, violation_flag (none|V1|V2|V?), confidence, evidence_quotes (short, with step refs), notes`

## 4. Scope

Code what the trace shows. Public data only.

## 5. Operational notes [proposed — for James to accept, change or reject]

These do not add categories. They make the draft above applicable the same way every time, by a person or by the LLM annotator.

**5.1 Unit of analysis [proposed].** One coding per trace. Within a layer, several codes may apply. A code may refer to any agent in the system; name the agent in `notes` if it matters.

**5.2 `failure_observed` field [proposed].** Before coding layers, record `yes`, `no` or `unclear`: does the trace show a failure at all? This is needed because the calibration set includes a few traces MAST judged failure-free (controls). If `no`, leave the code columns empty and set `deepest_layer` to `none`.

**5.3 Deepest contributing layer [proposed].** The deepest layer (L4 deepest, L1 shallowest) at which you coded a factor that contributed to the failure. This should normally equal the deepest layer you coded; the coding tools warn if it doesn't.

**5.4 Violation decision, step by step [proposed].** For each candidate unsafe act, ask in order:
- Q1. Was the requirement in the agent's accessible context (task text, system prompt, another agent's message, a tool result)? If no → error.
- Q2. Does the trace show the agent represented it (quoted, paraphrased, acknowledged, planned around it)? Or is the deviation one that cannot plausibly be accidental? If neither → error.
- Q3. Did the agent then proceed otherwise? If no → not an unsafe act at all.
- If Q1–Q3 all hold: `L1.V1` if the pattern recurs across the trace, `L1.V2` if it is a one-off; `L1.V?` if the evidence for Q1 or Q2 is thin.
- `violation_flag` summarises the L1 codes: `V2` if any `L1.V2`, else `V1`, else `V?`, else `none`.

**5.5 Benchmark information [proposed].** Some rendered steps are marked *NOT VISIBLE TO THE AGENTS* (correct answers, gold patches, the benchmark's own evaluation). Use them to understand what went wrong, but never as evidence for Q1 (what was in the agent's context).

**5.6 Evidence quotes [proposed].** Give 1–4 short quotes (up to ~25 words each) with step references, separated by ` | `, e.g. `[S4] "I will skip the tests for now" | [S9] "All tests pass"`. Every code you assign should be traceable to at least one quote or step reference.

**5.7 Confidence [proposed].** `high`: the evidence is explicit and you would expect another expert to agree. `medium`: a reasonable reading, but another expert could code a neighbouring category. `low`: the trace is ambiguous or truncated.

## 6. Open questions for v1 (James to decide)

1. **Test-harness defects.** Some traces fail because of the experiment's own set-up, not the agents: e.g. 5 traces where the task text is empty, so the agents had nothing to do. Code as L4 (the people who ran the system), add a code such as `L4.4` "evaluation/harness defect", or exclude such traces?
2. **Must every failure have an L1 code?** In HFACS every occurrence has an unsafe act. Is that true here, or can a failure be purely latent (e.g. a tool crashed and the agents responded reasonably)?
3. **Non-LLM components.** When the framework's own code misbehaves (e.g. a terminal that refuses to run anything without a code block), is that L2.1 Environment or L4.2 Resource provisioning?
4. **Repetition and loops.** MAST codes these as 1.3 Step Repetition. In AFACS, is a loop the L1 act of the agent repeating, the L3.3 failure of the orchestrator to break it, or both?
5. **Errors of omission.** Is "never verified the result" an L1 act, an L3.1 supervision failure, or an L4.1/L4.3 design absence? Where is the line?
