AFACS: HFACS for AI agents

AI agents fail a lot, and the standard study of why gives each failure one flat label. Aviation stopped doing that decades ago. This project applies HFACS layers and the error/violation distinction to 1,642 recorded agent runs, and measures whether that can be done reliably.

Data: MAST (Cemri et al., 2025)Framework: HFACS (Shappell & Wiegmann, 2000)Deadline: Thu 20 Nov

The questions AFACS asks

These are prompts for your judgement, not answers. The L4 question is now decided: codebook v1 adds L4.5 Operation set-up.

  • L4The people running the experiment sent an empty task. Whoever launched the run counts as part of the organisation, so this is L4.5 Operation set-up, and the trace is coded, not excluded.
  • L3Nothing in the system checks that a task exists before work starts. Is that a supervision gap?
  • L2Each agent took the previous agent's output at face value. Is that a coordination breakdown?
  • L1Could this be a violation? No: question 1 of the violation rule fails, because there was no requirement in the agents' context. At most it is an error.

The flat label records the most visible symptom. The layered coding asks where the defences had holes, and separates "could not" from "did not". Across hundreds of traces, that tells you what to fix.

The core contribution

Error or violation? The evidence rule

An error is an unintended deviation: a slip, a misreading, a bad decision on good information. A violation is a departure from a requirement the agent knew about. For AI this is roughly the line between a capability problem and an alignment problem. The rule decides it from the trace alone: it describes behaviour and makes no claim about what the model "wanted".

Cohen's κ

κ = (raw − chance) ÷ (1 − chance). Bands from Landis & Koch (1977): 0.21–0.40 fair, 0.41–0.60 moderate, 0.61–0.80 substantial.

Two rules the project follows. κ is computed separately for each code and then averaged, never on all codes pooled together: pooling counts the easy "no, no" answers as skill and inflates κ (on MAST's duplicates, pooling gives 0.54 against a correct 0.43). And with only 12 test traces, every κ comes with a 95% bootstrap interval, shown only where it means something.

The critical path

Your part: code 30 traces

Your expert coding is the reference standard. Claude is only trusted for the bulk run if it agrees with you on traces it was never tuned on. Your notes on where the codebook didn't fit become codebook v1.

Five traces per framework, shuffled into C01–C30. Four of the thirty are traces MAST judged failure-free (controls). Every framework has five rows, so you can't tell where they are, by design.

  1. Open a trace. data/calibration/C01.md. Read it end to end before coding.
  2. Fill in its row in annotations/human/calibration_sheet.csv: failure observed, codes per layer, deepest layer, violation flag, confidence, quotes with step numbers, and notes.
  3. Check the sheet now and then with uv run afacs-agreement check-sheet. It catches typos and inconsistencies.
  4. Keep going in order. About 129,000 words in all, roughly 12–15 hours. AG2 and MetaGPT traces take 5–15 minutes; the others 30–60. If time runs short, stop where you are: the order is random, so a partial set stays balanced.

Keep it blind

  • Don't open data/processed/calibration_key.csv. It says which traces are controls and which are held out for testing.
  • Don't look up MAST's labels for these traces.
  • Benchmark answers are hidden while you code. Look at them only after all 30 are done.
