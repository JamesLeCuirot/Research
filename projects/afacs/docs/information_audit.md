## Findings

- **Present almost everywhere:** User prompts, Model responses and actions, Tool errors & limitations. The logs are good records of what the agents said and did.
- **Absent in every framework:** System docs & change logs, System artifacts, Model & system access (e.g., API)*. Nothing in MAST lets an investigator identify, or re-run, the exact system that failed.
- **Never fully present:** System configurations (e.g., seeds, version, temperature)*, Tool identification & version. Each is at best partial, and only in some frameworks.
- **Logging depends on the framework, not on the failure.** ChatDev and OpenManus log far more about their own workings than AG2 or MetaGPT. What an investigator can establish therefore varies with the software that happened to produce the trace.
- **Hidden reasoning is never logged.** Where reasoning is visible at all, it is what the model chose to write into its output (OpenManus 'thoughts', HyperAgent 'Thought:'), which Ezell et al. note may not reflect the model's actual reasoning.

### Failures the logs record outside the agents

OpenManus's logs record events that no agent message would show: the harness timing out after one hour (24 of 30 runs), errors from the model provider's API (14 runs) and the framework detecting a stuck agent (11 runs). These are candidate causes above the agent (resource limits, environment), visible only because this framework logs its own components.

### What MAST's metadata adds outside the logs

It provides: framework name (mas_name); model name without version (llm_name: 'GPT-4o', 'GPT-4o-mini', 'Claude', 'Qwen', 'CodeLlama'); benchmark name (benchmark_name; wrong for OpenManus and imprecise for AG2 GSM-Plus); an index within each group (trace_id; not unique across groups); 14 MAST failure-mode labels from an LLM judge.

It does not provide: model versions or snapshot dates; run timestamps or unique run identifiers; sampling parameters and seeds; framework versions; task outcome (success or failure on the benchmark); system prompts or agent configurations.

## Implications for reconstruction and analysis

- **No incident in this dataset can be re-run exactly.** Model versions are unknown, sampling settings and seeds are logged only in ChatDev (and seeds nowhere), and no system artifacts are available.
- **The task itself is not always recoverable.** OpenManus logs print only the start of the task (29 of 30) or omit it (1 of 30), and 5 traces across MetaGPT and ChatDev have an empty task (see `docs/data_audit.md`).
- **Duplicated and mislabelled logs** (data audit) mean that even the link between a log and its metadata cannot be taken for granted.
- **Supervision and coordination are visible; their configuration is not.** Agent-to-agent messages are well logged, so a coder can see an orchestrator fail to correct an error, but without system prompts or role definitions it is often impossible to tell whether the orchestrator was ever instructed to check.

## Automatic detectors

- System prompts: role or phase prompts logged ('assistant_role_prompt', 'phase_prompt').
- User prompts: the full task text is logged (not empty, truncated or missing).
- External information: retrieved web pages, files, repository code or app data appear in the log.
- Scaffolding component logs: log records written by the framework itself.
- Model reasoning traces: a labelled reasoning section ('thoughts:' field or ReAct 'Thought:').
- Model responses and actions: at least one agent output.
- Log metadata (e.g., timestamps, identifiers, location): timestamps on log lines or a run identifier.
- System configurations (e.g., seeds, version, temperature)*: sampling parameters, a model identifier or scaffolding versions.
- Tool identification & version: tool calls by name.
- Tool actions & services enabled: a list of the agents' or tools' available capabilities.
- Documentation & usage guides: tool documentation requested and logged (api_docs.show_api_doc).
- Access requirements (e.g., API keys): credentials retrieved in the trace.
- Personalization & stored data: user profile or memory settings.
- Tool state details: reports of a tool's state (browser page, viewport).
- Tool errors & limitations: tool, execution or API errors recorded in the log (share = traces in which at least one occurs).
